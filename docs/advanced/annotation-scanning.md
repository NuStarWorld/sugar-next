# 注解扫描机制

Context 的组件扫描不是简单地加载包下所有类。它会先读取 class 字节码，判断是否可能是组件，再加载符合条件的类。

## 为什么不用反射直接扫

直接加载所有类有几个问题：

- 触发静态初始化。
- 加载无关类。
- classpath 大时成本高。
- 缺少依赖时更容易提前失败。

先读字节码能降低这些副作用。

## 扫描来源

扫描包来自：

- 宿主类所在包。
- `@Scan` 指定的包。
- 带有 `@Scan` 元注解的启动注解所在 jar。

## 判断组件

扫描过程中会读取 class 上的注解，并判断：

- 是否直接标注 `@Component`。
- 是否标注了带 `@Component` 的派生注解。

只有可能是组件的类才会进入后续加载和 Bean 注册流程。

## 依赖过滤

`@DependsOn` 可以让某些组件在依赖 class 或属性不存在时跳过注册。

这是可选能力的正常表达方式。不要用它隐藏强依赖。

## 性能注意事项

- 扫描 jar 是 IO 操作，包范围越大越慢。
- 扫描结果依赖 `JavaCache`，重复解析 class 会浪费性能。
- 不要把扫描包设成过大的根包，例如整个公司公共包。
- 组件注解应该清晰，别搞多层元注解迷宫。
