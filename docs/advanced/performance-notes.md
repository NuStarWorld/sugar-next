# 性能与内存说明

本文档记录 Sugar Next 使用时需要注意的性能和内存问题。

## Context 扫描成本

组件扫描需要遍历 jar 或 classpath，并读取 class 字节码。扫描包越大，IO 和解析成本越高。

正确做法：

- 缩小 `@Scan` 范围。
- 避免扫描无关公共包。
- 复用字节码解析缓存。

愚蠢做法：

- 扫整个根包。
- 把大量无关类塞进扫描路径。
- 希望容器替你过滤所有混乱结构。

## JavaCache

`JavaCache` 用于缓存 `JavaClass` 解析结果。大量扫描时不复用缓存，就是重复读 class 文件，纯浪费。

## 反射代理

`reflect` 模块内部会缓存字段、方法和构造器的访问句柄。第一次调用通常成本更高，后续调用较低。

仍然要记住：反射代理不是普通方法调用。热路径里高频调用私有反射成员，设计上就值得怀疑。

## 表达式计算

`Expression` 支持预编译。

高频计算应该：

- 复用 `Expression`。
- 先调用 `compile()`。
- 只替换变量上下文。

不要每次计算都 new 一个表达式。

## EventBus

订阅者集合适合读多写少。

频繁发布事件没问题，频繁注册和取消订阅不合适。动态订阅如果非常频繁，应该改成稳定订阅者内部判断条件。

## IOUtils

`readAllBytes` 会把整个流读入内存。大文件这么用会直接制造内存压力。

大文件应使用 `transferTo` 或自定义流式处理。

## Bean 数量

大量 Bean 会增加：

- 扫描时间
- 元数据存储
- 单例初始化时间
- destroy 阶段清理成本

不要把每个微小工具类都注册成 Bean。没有生命周期和依赖注入需求的静态工具，不该进容器。
